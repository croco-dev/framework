# Package the Problem registry without declaration source locations

## Context

- `scripts/problem-registry.mts` writes the same registry to `docs/problem-code-registry.json` and to
  `packages/problems-core/src/generated/problem-code-registry.ts`. Every entry carried `sources`, the file, line
  and column of the declaration, and `dynamicCodeFactories` carried the same for a class (`28a8c89`).
- The TypeScript module is a build input of `@croco/problems-core`. 149 workspace manifests depend on that
  package directly, and Turbo hashes a task together with the tasks it depends on. Appending one line to the
  module changed 500 of 508 `build` and `test:evidence` task hashes (`turbo run --dry=json` at `6b0300f`).
- Moving a Problem declaration by one line in any package rewrites its `line`. Of the 100 commits before
  `6b0300f`, 29 rewrote the module, and 13 of those changed only `file`, `line` or `column` values.
- The package reads the registry at runtime in one place, to map a code to its redaction policy
  (`ProblemResponseRedaction.ts`). No package source reads `sources` from the packaged constant (searched
  `packages/*/src` outside generated files and docs). `croco doctor`, the changed-test plan and the docs example
  check read the JSON file. Readers outside this repository are unknown.
- `tsconfig/contract-strict.baseline.json` is regenerated by the strict contract typecheck and sat under the
  Turbo global dependency `tsconfig/**`. Its only readers are `scripts/strict-contract-typecheck.mts` and the
  release gate. Changing it changed 508 of 508 task hashes; 4 of the same 100 commits changed it.

## Decision

- The packaged module omits `sources` from every Problem entry and `source` from every
  `dynamicCodeFactories` entry. `CrocoProblemRegistry` changes with it. Codes, categories, statuses, recovery
  metadata, lifecycle and cookbook paths stay. The JSON registry keeps every source location and remains the
  artifact that tools and people read for them.
- The module is checked against `PackagedProblemCodeRegistry`, which `ProblemRegistry.ts` exports for the
  generated file only; it is not part of the package entrypoint. `ProblemCodeRegistry` keeps `sources` because
  it describes the full registry that `createProblemCodeRegistry()` builds and validates.
- `turbo.json` excludes `tsconfig/contract-strict.baseline.json` from the global dependencies. The shared
  `tsconfig.*.json` presets still invalidate every task.
- Rejected: moving the registry constant and its types into a leaf package. It removes the remaining
  invalidations, but redaction would need each Problem class to carry its own policy, which changes how a
  response built from a bare code is redacted, and it removes a public export instead of narrowing a type.
- Rejected: leaving the registry as it is and excluding only the strict baseline. That removes 4 of 36
  full-graph invalidations.

## Consequences

- A change that only moves a Problem declaration rewrites the JSON registry and the cookbook, not the packaged
  module. Shifting a declaration in `storage-r2` by two lines changed 7 of 691 task hashes (`storage-r2` and
  `docs`).
- Adding or changing a Problem code still rewrites the module and invalidates every dependent. That is correct:
  the redaction map compiled into `@croco/problems-core` changes.
- Reading `sources` from an entry of the registry constant that `@croco/problems-core` exports no longer
  typechecks and returns `undefined` at runtime. The changeset records it as a minor change with the JSON file
  as the replacement.
- `assertProblemCodeRegistryValid()` no longer accepts the packaged constant as is, because it validates source
  locations. The `problems-core` test gives each packaged entry a placeholder location and runs the validator, so a
  pull request that changes the runtime category mapper fails in that package's own test when the registry's
  statuses or titles no longer match. `scripts/tests/problem-registry.spec.ts` also runs the validator over
  `docs/problem-code-registry.json` with its real locations; change-scoped CI selects it only when `scripts/`
  changes. The JSON is not a `problems-core` input, because that would bring back the invalidation this change
  removes.
- A file added under `tsconfig/` that is not a shared preset must be excluded from the global dependencies the
  same way, or it invalidates every task.
