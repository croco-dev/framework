# Task 12 Enforcement Matrix

Date: 2026-04-22
Branch: framework-tech-health-enforcement

## 목적

Task 7~11에서 추가된 warning-only 또는 onboarding 보강 결과를 한데 모아, 각 트랙이 언제 `warning-only`에서 `enforce`로 전환될 수 있는지 명문화한다.

## 공통 원칙

1. baseline이 아직 열려 있거나 false positive 관리 절차가 검증되지 않았으면 즉시 `enforce`로 올리지 않는다.
2. `warning-only` 단계는 기존 hard gate를 대체하지 않고, 신규 신호를 수집·안정화하는 용도로만 사용한다.
3. `enforce` 전환은 단일 green run이 아니라 여러 PR/여러 실행에서 재현된 안정성 증거가 있어야 한다.
4. `rollback`은 단순 실패 1회를 뜻하지 않는다. 오탐 급증, 변동성 증가, 실행 시간 급증처럼 팀 생산성을 해치는 조건이 확인될 때만 수행한다.

## 현재 CI 통합 상태

- `validate` job:
  - Security audit warning report (`continue-on-error: true`)
  - Secret scan warning report (`continue-on-error: true`)
  - Dependency audit (기존 hard gate 유지)
  - Architecture circular dependency warning (`continue-on-error: true`)
  - Biome / Build / TypeScript / Test
  - Core package coverage warning report (`continue-on-error: true`)
  - Core package coverage gate (기존 hard gate 유지)
- `benchmark` workflow:
  - `BENCHMARK_GATE_MODE=warning-only`
  - benchmark step는 `continue-on-error: true`
  - artifact/comment는 항상 유지
  - enforce mode일 때만 마지막 hard fail step 활성화
- DX track:
  - CI에 새 step을 추가하지 않았고, `pnpm setup`, `.env.example`, `CONTRIBUTING.md`로 로컬 onboarding 진입점을 정리했다.

## 트랙별 전환 해석

### 1. Architecture
- 현재 단계: baseline 공개 + warning-only 수집
- enforce 후보 시점: 기존 5건 순환 의존 정리 후, 신규 cycle 유입만 차단하는 것이 아니라 전체 결과가 안정적으로 0 또는 승인 예외 목록으로 수렴했을 때
- 전환 방식: `continue-on-error: true` 제거 또는 실패 후속 step 추가
- 주의: baseline 5건이 남은 상태에서 enforce 전환하면 저장소 전체가 구조적으로 항상 fail하는 상태가 된다.

### 2. Coverage
- 현재 단계: report + hard gate 병행
- enforce 후보 시점: 현재 core 5개 패키지는 이미 hard gate가 있으므로, 다음 전환은 “대상 확대”가 핵심이다.
- 전환 방식: 추가 패키지군에 baseline을 먼저 수집한 뒤 threshold를 순차 편입
- 주의: repo-wide 일괄 강제는 false alarm과 유지비를 키우므로 금지

### 3. Security
- 현재 단계: dependency는 hard gate 유지, secret scan은 warning-only
- enforce 후보 시점: secret scan false positive 관리가 안정화되고, dependency backlog가 “새 위반 탐지만 차단” 가능한 수준으로 줄어든 이후
- 전환 방식: 먼저 gitleaks만 enforce로 승격하고, dependency audit는 backlog 정리 후 severity/범위를 재조정
- 주의: backlog 104건이 열린 상태에서 새 hard gate를 추가하면 모든 PR이 기존 부채 때문에 막힐 가능성이 크다.

### 4. Performance
- 현재 단계: genuine warning-only
- enforce 후보 시점: skip 6건 threshold 정의 완료 + 여러 PR에서 분산이 안정적으로 관찰된 이후
- 전환 방식: 현재 구조를 유지한 채 `BENCHMARK_GATE_MODE=enforce`로 전환
- 주의: comment/artifact를 제거하지 않고 hard fail만 복구해야 한다.

### 5. DX
- 현재 단계: onboarding 기반 정비 완료, 아직 CI enforce 없음
- enforce 후보 시점: 문서-스크립트 일치성이 유지되고, onboarding smoke check의 비용 대비 효과가 확인된 이후
- 전환 방식: 전체 `pnpm setup`를 매 PR에 강제하기보다 문서 링크/예제 파일/필수 스크립트 존재 여부 같은 저비용 검증부터 도입
- 주의: DX는 false positive보다 실행 비용이 문제다. 비싼 검증을 곧바로 hard gate로 두지 않는다.

## false positive 관리 원칙

1. **Architecture**: 결과가 실제 cycle인지 확인 후, 예외가 필요하면 임시 무시는 전체 디렉터리가 아니라 최소 path 단위로 제한한다.
2. **Coverage**: flaky test로 생긴 일시 하락과 실제 coverage regression을 구분한다. 변동 원인이 불안정 테스트면 threshold 확대를 멈춘다.
3. **Security**: `.gitleaksignore`/allowlist는 fingerprint 또는 path 최소 범위만 허용한다. 광범위 glob ignore는 금지한다.
4. **Performance**: threshold 미정의 또는 환경 민감 benchmark는 먼저 측정 안정화 후 fail 대상에 포함한다.
5. **DX**: 문서와 실제 명령이 어긋나는 문제를 false positive로 취급하지 않고, smoke check 범위 자체를 최소 비용 검증으로 설계한다.

## rollout 조건

enforce 승격은 아래 공통 조건을 모두 만족할 때만 진행한다.

1. warning-only artifact 또는 report가 여러 실행에서 반복 재현된다.
2. baseline backlog가 “기존 부채 때문에 항상 실패”하는 수준이 아니다.
3. false positive 예외 목록이 최소 범위로 안정화됐다.
4. CI 추가 시간이 팀 허용 범위 안이다.
5. 기존 hard gate는 제거하지 않고, 필요한 경우 신규 enforce를 별도 단계로 추가한다.

## rollback 조건

아래 중 하나라도 만족하면 warning-only 또는 이전 단계로 되돌린다.

1. unrelated PR 다수가 동일 gate 때문에 반복 차단된다.
2. false positive 예외가 넓어져 gate 신뢰성이 떨어진다.
3. 실행 시간 증가가 병목이 되어 전체 CI 체감 속도를 크게 해친다.
4. baseline이 충분히 안정화되지 않았다는 새 증거가 나온다.
5. artifact/report 검토 결과가 실제 행동으로 이어지지 않아 hard fail의 실효성이 낮다고 판단된다.
