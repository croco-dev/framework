# Page experience

This loopback-only synthetic example compares three known sessions: a preview followed by a committed purchase, an observed non-engaged session, and a session with ten visible seconds after the hero appeared. It uses the production calculator, browser collector and administrator Panel. No credentials, customer events or database are required for standalone calculation.

Run `pnpm --filter @croco-example/page-experience dev` and open the printed local URL. `pnpm --filter @croco-example/page-experience test` verifies the known counts; `pnpm --filter @croco-example/page-experience test:browser` starts its own temporary server and verifies StrictMode collection, keyboard refresh, all Panel states and desktop/mobile layouts in headless Chrome. Screenshots are written to the OS temporary directory. The example deliberately provides synthetic aggregate reports; it is not a production authentication or collection endpoint.

`PageExperienceDefinition` fixes the page, observable content condition and minimum intersection ratio, foreground visible-time threshold, qualifying actions, one value action, distinct unit, session window and timezone. A session's start belongs to `[from,to)`; its observations may extend to the declared session deadline. UTC instants and the named reporting timezone are retained. `session`, `subject` and `pageInstance` are separate units. The ordered funnel is calculated per actual page instance before distinct units are counted. A confirmed value action prevents an automatic bounce; a missing client attempt still leaves the domain outcome visible separately.

Create one collector for each actual navigation outside React effects, then pass it to `usePageExperience`. Keep that collector through hydration and StrictMode effect replays; prefetch and server rendering must not call `start`. Wire a real `IntersectionObserver` to `contentDisplayed(intersectionRatio)`, and call `observe` when the application wants to record a cumulative visible-time sample. Hidden time is excluded. Supply a monotonic duration clock separately from the wall-clock timestamp, and register the allowed engagement/value actions; raw URL configuration and unknown actions are rejected. A long-running page should flush at application-controlled boundaries. `send` must enforce its transport deadline and use the server collection endpoint; the example keeps observations in memory for inspection. No cookies, local storage, fingerprinting, raw URLs or arbitrary event properties are collected. The host owns consent and must revoke collection, buffered data and in-flight transport when permission changes. Buffers, duplicate action references and retries are bounded; status exposes drops.

On the server, `PageExperienceCollection.observe` accepts only the allowlisted browser shape and binds app/environment/tenant, subject and session from authenticated server context. The host validates origin and body size before decoding HTTP, then supplies current authorization and collection consent. Never construct that context from browser fields. Session records come from the same server session owner; a browser observation does not create a session population. The `append` callback reuses the existing source/outbox/warehouse path, owns retention and deletion, and must deduplicate `(scope, source, id)` with conflict detection. Do not treat its acceptance as durable publication.

Call `committed` only after the domain transaction commits or from the existing transactional outbox. `verifyReceipt` must read the domain-owned receipt under current scope and subject authority; rollback or an unknown receipt returns no verified record. Browser click, successful HTTP status and client trace identifiers are never proof. `unavailable` is a retryable observation failure and must not turn an already completed purchase into a business failure. Receipt retention and suppression remain owned by the domain/source. The class does not introduce an event bus or a receipt database.

For files, `importPageExperienceSource` uses `@croco/etl-core/source`; its ten flat fields are `PAGE_EXPERIENCE_FIELDS`. Scope, definition, session coverage, deletions, cutoff and source revision are trusted metadata outside the file. Only a trusted receipt bridge can produce `committed` rows; uploading arbitrary JSONL is not domain verification. `readPageExperienceWarehouse` uses the existing pinned `WarehouseReader` with row/byte/page bounds, current epochs and exact page identity. It creates no SQL client. The native integration test in `warehouse-postgres` installs an isolated PostgreSQL fact schema, writes, seals and publishes a snapshot, reads it with two-row pages, compares calculation results, and rejects foreign tenant/current privacy changes. Enable it with `CROCO_TEST_REAL_RESOURCES=1 pnpm --dir packages/warehouse-postgres exec vitest run src/tests/PageExperience.integration.spec.ts`.

Register fixed trusted source metadata with `registerPageExperienceQuery` and execute it through `MetricReadService`. The shared runner owns current read/export/report permissions, budgets, immutable snapshot matching, verified-report provenance and privacy epochs. Its authorized partial result contains only aggregates. Do not forward raw file rows from a browser to this callback. A host must re-resolve current suppression and deletion evidence before each source load and invalidate retained reports when those epochs change. Hashes identify definitions and inputs; they do not prove that a source is authentic. No report persistence, SQL runner or cache is added here.

`completeThrough` and complete population coverage are required to infer non-engagement. Open sessions and unknown coverage remain separate; zero denominators produce `null`, not zero or 100%. Events received after cutoff are absent from that revision. Events beyond allowed lateness are counted as excluded; an accepted late arrival changes the report's input hash/revision. A new revision requires a new immutable source snapshot/declaration. These are observed associations, not causal explanations for abandonment.

GA4 import preserves its own session denominator, engaged sessions, period, timezone, filters and provider/settings/source versions. Custom visible-time results are never called GA4 engagement or bounce. No GA4 SDK is included.

The calculator and declarations require no host capabilities. The browser helper and Panel run in the browser; server collection and reads require application-owned authorization, lifecycle and existing providers. Kubernetes, Lambda and Workers deployments have not been certified by this local fixture. Await source writes/flushes before a Lambda boundary; a PostgreSQL provider still needs its own host-compatible connection path. No live infrastructure or npm release is claimed.
