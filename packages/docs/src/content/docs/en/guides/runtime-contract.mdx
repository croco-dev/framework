---
title: Runtime Contract
description: Use one request runtime context across Node, AWS Lambda, and Cloudflare Workers.
---

Croco exposes adapter runtime details through `Context.getRuntimeContext()` from
`@croco/framework-context`. Application code can read one request-scoped contract without depending on
Node, API Gateway, or Workers-specific objects.

The contract is provided by Croco-owned entry points such as `createApp().fetch()`, `lambdaHandler()`,
`toWorkersHandler()`, and the default `createWorkerFetchHandler()` path in the Cloudflare preset.
Explicit raw Hono forwarding remains a compatibility path and does not provide this runtime contract.

```typescript
import { Context } from "@croco/framework-context";
import { Controller, Get } from "@croco/protocols-rest";

@Controller("/runtime")
class RuntimeController {
  @Get("/context")
  context() {
    const runtime = Context.getRuntimeContext();

    runtime?.waitUntil(Promise.resolve());

    return {
      platform: runtime?.platform,
      requestId: runtime?.requestId,
      canUseEnv: runtime?.capabilities.env,
      canUseWaitUntil: runtime?.capabilities.waitUntil,
    };
  }
}
```

## Capability Matrix

| Capability         | Node HTTP                        | AWS Lambda                                                           | Cloudflare Workers                          |
| ------------------ | -------------------------------- | -------------------------------------------------------------------- | ------------------------------------------- |
| `platform`         | `node`                           | `lambda`                                                             | `cloudflare-workers`                        |
| `env`              | supported through `process.env`  | supported through `process.env`                                      | supported through the Worker binding object |
| `filesystem`       | supported                        | supported for the Lambda filesystem, including `/tmp`                | unsupported                                 |
| `nodeApi`          | supported                        | supported on the Node.js Lambda runtime                              | unsupported                                 |
| `requestLifecycle` | supported per HTTP request       | supported per invocation                                             | supported per fetch event                   |
| `requestId`        | `x-request-id` or generated id   | API Gateway request id or `awsRequestId`                             | `x-request-id` or generated id              |
| `logger`           | app logger                       | app logger                                                           | app logger                                  |
| `trace`            | active HTTP server span          | active HTTP server span                                              | `traceparent` when present                  |
| `waitUntil`        | unsupported                      | queued and drained before response conversion                        | delegates to `ExecutionContext.waitUntil`   |
| `flush`            | unsupported                      | drains queued work and can run transport-provided telemetry flushing | unsupported                                 |
| `shutdown`         | unsupported in the request scope | unsupported in the request scope                                     | unsupported in the request scope            |

The code-level source of truth for these runtime and capability names is
`RUNTIME_CAPABILITY_SUPPORT` from `@croco/framework-context`. `RuntimeContextInit<"cloudflare-workers">`
cannot declare `flush: true` or provide a `flush` hook, while `RuntimeContextInit<"lambda">` can declare
`flush: true` only with a concrete flush implementation.
Custom adapter platforms can still use a custom `platform` string, but they must pass an explicit
capability support config when creating a runtime context so unsupported hooks are rejected instead of
falling back silently.

## Native Context

Use `runtime.native` only at adapter boundaries:

- Lambda stores `{ event, lambdaContext }`.
- Cloudflare Workers stores `{ executionContext }`.

Prefer capability checks before reading runtime-specific objects. Missing features are represented as
`capabilities.<name> === false` and no-op hooks, not as hidden platform assumptions.
Adapter authors must not advertise unsupported capabilities as available. Croco rejects erased JavaScript
inputs that claim a platform/capability combination the matrix does not support or claim a hook-backed
capability without a hook implementation.

## Lambda Telemetry Flush

`runtime.flush()` drains Croco runtime work queued through `runtime.waitUntil()`. OpenTelemetry export stays
owned by `@croco/telemetry-sdk-node`, so Lambda apps should connect `TelemetryRuntime.forceFlush()` at the
transport boundary:

```typescript no-check
import { TelemetryRuntime, lambdaPreset } from "@croco/telemetry-sdk-node";

const telemetry = TelemetryRuntime.getInstance();
await telemetry.init(lambdaPreset({ serviceName: "orders" }));

export const handler = app.lambdaHandler({
  flush: async () => {
    const result = await telemetry.forceFlush(5000);
    if (!result.success) {
      throw result.error ?? new Error("telemetry flush failed");
    }
  },
});
```

The callback runs after the request and queued runtime work complete. If it rejects, the Lambda handler rejects
instead of returning a business success without export evidence.
