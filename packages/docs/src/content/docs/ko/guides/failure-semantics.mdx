Croco는 실패를 타입 있는 복구 계약으로 다룹니다. 실패는 Croco 패키지 경계를
넘기 전에 도메인 결정, 클라이언트 입력 문제, 일시적 의존성 장애, timeout, 취소,
idempotency 충돌 중 무엇인지 알려야 합니다. 그 결정은 `Problem` 카테고리, 안정
코드, transport 안전한 응답 형태로 보여야 합니다.

## 핵심 규칙

- 예상되는 도메인, 검증, 인가, quota, 제공자, timeout, 취소, idempotency,
  프레임워크 계약 실패에는 Croco `Problem`을 throw하세요.
- 일반 `Error`는 예상 밖 구현 결함만을 나타냅니다. transport가 불투명한 500으로
  바꿀 수는 있지만, 패키지 API는 호출자가 복구할 수 있는 상태를 일반 `Error`로
  쓰면 안 됩니다.
- `ProblemCategory`는 작고 공유되게 유지하세요. "어떤 복구가 가능한가"에 답합니다.
- `code`는 패키지별로 안정적이게 유지하세요. "정확히 어떤 실패인가"에 답합니다.
- 제공자 실패를 정규화할 때는 `cause`나 안전한 extensions에 상위 실패 근거를
  보존하세요. 시크릿, 자격 증명, 원시 요청 본문, tenant 비공개 데이터를 포함하지
  마세요.
- 실패가 발생했는데 빈 성공 결과를 반환하지 마세요. 타입 있는 실패나 출처가
  호출자에게 보이는 명시적 복구 값을 사용하세요.

## 카테고리와 코드 이름 짓기

`ProblemCategory`는 패키지를 가로지르는 복구 분류입니다. 새 패키지 실패는 제공자나
도메인마다 좁은 카테고리를 추가하기보다 가장 가까운 기존 카테고리를 고르세요.

| 카테고리                     | 용도                                                 | 기본 재시도 결정                       |
| ---------------------------- | ---------------------------------------------------- | -------------------------------------- |
| `BadRequest`                 | 잘못된 요청 형태, 잘못된 원시 형식, 미지원 옵션      | terminal                               |
| `Unauthorized` / `Forbidden` | 인증 주체 부재 또는 권한 부족                            | terminal                               |
| `NotFound` / `Gone`          | 없거나 폐기된 리소스                                 | terminal                               |
| `Conflict`                   | 중복 상태, 낙관적 동시성, idempotency 충돌           | 호출자가 입력을 바꾸지 않으면 terminal |
| `ValidationError`            | 스키마·필드 검증 실패                                | terminal                               |
| `BusinessRuleViolation`      | 재시도하면 안 되는 도메인 정책 거부, quota 정책 거부 | terminal                               |
| `TooManyRequests`            | rate limit, 열린 circuit, 호출자가 백오프해야 함     | 기본 재시도 가능                       |
| `InternalServerError`        | 일시적 제공자·런타임·프레임워크 인프라 실패          | 기본 재시도 가능                       |
| `NotImplemented`             | 미지원 capability나 어댑터 기능                      | 명시적 opt-in이 없으면 terminal        |

`code`는 릴리스에 걸쳐 안정적이어야 하며 로그, 테스트, 생성 클라이언트에 쓸 만큼
구체적이어야 합니다. 보통 `RETRY_EXHAUSTED`, `CIRCUIT_BREAKER_OPEN`,
`LAMBDA_TIMEOUT_GUARD` 같은 기존 패키지 관례의 대문자·패키지 접두 코드를
선호하세요. 요청 id, tenant id, 제공자 trace id, 현지화 문구, 바뀔 수 있는 제공자
메시지를 코드에 넣지 마세요.

## 재시도 가능성

`@croco/retry-core`는 Croco `Problem` 카테고리를 직접 소비합니다. 기본 정책은
`InternalServerError`와 `TooManyRequests`를 재시도하고, 클라이언트/도메인
카테고리는 재시도하지 않으며, `TypeError`, `ReferenceError`, `SyntaxError`,
`RangeError` 같은 프로그래머 오류를 거부합니다.

오류의 명시적 분류가 카테고리보다 우선합니다.
`@croco/problems-core`의 `readExplicitRetryability()`는 최상위 `retryable`
불리언을 먼저 읽고 `extensions.retryable`을 다음으로 읽습니다. 다른 값은 분류
없음으로 취급합니다. retry-core 기본 정책이 이를 사용하므로,
`extensions.retryable: false`인 제공자 Problem은 한 번만 실행되고,
`extensions.retryable: true`인 `Conflict` Problem은 시도가 남았으면 재시도합니다.
QStash 트리거는 항상 같은 함수로 실패를 분류합니다. idempotency 핸들러 실패와
saga 단계도 기본적으로 이를 사용합니다. 호출자가 준 idempotency `isRetryable`이나
saga 단계 `retry.shouldRetry`가 이를 대체합니다. retry-core 기본 정책에서는
`noRetryFor`가 여전히 우선합니다. 기본 프로그래머 오류(`TypeError`,
`ReferenceError`, `SyntaxError`, `RangeError`)는 `retryable: true`를 선언해도
재시도되지 않습니다. retry-core는 `Error`가 아닌 throw 값을 `Error`로 감싸서
분류하므로, `Error` 인스턴스의 플래그만 정책에 도달합니다.

즉 패키지 작성자는 retry가 보기 전에 예상 실패를 분류해야 합니다:

```typescript no-check
import { Problem, ProblemCategory } from "@croco/problems-core";

class ProviderUnavailableProblem extends Problem {
  constructor(cause: Error) {
    super(
      "PAYMENTS_PROVIDER_UNAVAILABLE",
      ProblemCategory.InternalServerError,
      "Payments provider failed",
      {
        cause,
      },
    );
  }
}

class PaymentLimitExceededProblem extends Problem {
  constructor() {
    super(
      "PAYMENT_LIMIT_EXCEEDED",
      ProblemCategory.BusinessRuleViolation,
      "Payment limit exceeded",
    );
  }
}
```

제공자 실패는 기본 재시도 가능입니다. 비즈니스 규칙 실패는 기본 terminal입니다.
호출자가 다른 재시도 정책을 선택할 수는 있지만, 패키지의 기본 분류는 호출자별
오버라이드 없이 정확해야 합니다.

## Timeout과 취소

Timeout과 취소는 제어 평면 실패입니다. 추가 부수 효과를 멈추고 복구 로직을 위해
사유를 보존해야 합니다.

- `LambdaTimeoutGuard`는 다음 재시도 시도를 시작하기 전에 실패하고 Croco
  `Problem`인 `LambdaTimeoutProblem`(코드 `LAMBDA_TIMEOUT_GUARD`)을 throw합니다.
- 열린 circuit 실패는 `TooManyRequests`의 `CircuitBreakerOpenProblem`을
  throw합니다. 호출자가 circuit을 도메인 거부로 취급하지 않고 백오프할 수
  있습니다.
- 패키지가 signal을 받으면 abort signal을 제공자 호출에 전파해야 합니다.
  패키지가 수명주기 상태를 기록한다면, 취소는 failed나 completed가 아니라 명시적
  cancelled 상태로 옮겨야 합니다.
- 부수 효과가 커밋된 것으로 알려지지 않았다면, timeout이나 취소가 멱등 작업을
  성공으로 표시하면 안 됩니다.

## Idempotency

Idempotency는 재시도 정책 그 자체가 아니라 상태 계약입니다.

- 완료된 idempotency 키는 기록된 성공을 리플레이하거나 기록된 타입 실패를
  반환할 수 있습니다.
- 진행 중인 키는 결정적인 충돌이나 busy 상태 `Problem`으로 실패해야 합니다.
  호출자는 문서화된 복구 창 뒤에 재시도할 수 있습니다.
- 부수 효과가 시작된 뒤 완료 기록 전에 저장소가 실패하면, 안전할 때 진행 중
  표시를 중단하거나 지워야 합니다. 부분 상태를 일반 오류 뒤에 숨기면 안 됩니다.
- 리플레이된 연산은 원래 결과를 만든 tenant, meter/리소스 id, idempotency 키
  경계와 같아야 합니다.

`@croco/metering-core`는 quota 실패, 중복 레코드, idempotency 정리를 일반 저장소
오류와 분리해서 이 패턴을 따릅니다.

## Transport와 클라이언트 소비

HTTP와 RPC transport는 `Problem` 상세를 생성 클라이언트가 소비할 수 있는 실패
union 형태로 보존해야 합니다. transport는 알 수 없는 일반 오류를 불투명한 500
응답으로 바꾸고 원본 오류를 로그할 수 있지만, 예상 실패는 transport에 닿기 전에
이미 타입이 있어야 합니다.

생성된 `@croco/rpc-codegen` 클라이언트는 이 구분을 명시적으로 모델링합니다.
본문이 `RpcProblemDetails`와 일치하는 non-2xx 응답은 `RpcClientProblemError`로
reject되며, 호출자는 `error.problem.code`, `error.problem.status` 등의 안전한
`Problem` 필드로 분기해야 합니다. 비었거나 유효하지 않거나 비 Problem 오류
응답은 `RpcClientResponseError`로 reject됩니다. 호출자는 일반 `Error.message`를
파싱하지 말고 transport/프로토콜 실패로 다뤄야 합니다.

패키지별 차이는 의도적입니다:

- `@croco/problems-core`는 안정 `Problem` 봉투와 카테고리-상태 매핑을 정의합니다.
- `@croco/retry-core`는 카테고리를 소비해 재시도 가능성을 정하고, 복구 로직용
  retry/timeout/circuit `Problem` 타입을 방출합니다.
- `@croco/transports-http`는 알려진 `Problem` 인스턴스를 RFC 7807 응답으로
  직렬화하고, 비 Problem 오류를 처리되지 않은 내부 결함으로 다룹니다.
- `@croco/protocols-graphql`은 `Problem`을 HTTP와 같은 코드 우선 redaction
  정책의 GraphQL `errors` 메타데이터로 바꿉니다. 공개·안전 메시지 Problem은
  안전한 상세와 허용 extensions를 유지하고, 운영자 전용 Problem은 Problem
  extensions 없이 불투명 메시지를 반환합니다.
- `@croco/transports-graphql`은 GraphQL Yoga가 resolver나 컨텍스트 Problem에 이
  변환을 적용하도록 설정합니다. `GraphQLError.originalError` Problem도
  포함됩니다. 다른 오류는 Yoga 기본 마스킹 동작을 유지합니다. GraphQL은 RFC 7807
  본문 대신 `errors` 봉투와 resolver 경로를 유지하며, 런타임 오류 extensions에
  `requestId`, `traceId`, 텔레메트리, `redactionPolicy`를 절대 노출하지 않습니다.
  Yoga의 서버 측 로거는 Croco Problem에 같은 redaction을 적용합니다. 운영자는
  비 Problem 실패에 배포별 시크릿 처리가 여전히 필요합니다.
- `@croco/rpc-codegen`은 직렬화된 `Problem` JSON을
  `RpcClientProblemError.problem`으로 바꾸고, 비 Problem 실패는
  `RpcClientResponseError`로 분리합니다.

GraphQL 계약 스냅샷에는 선언된 Problem 응답의 redaction 정책이 포함됩니다. 해당
메타데이터는 생성 Problem 레지스트리에서 코드로 카테고리 fallback과 함께
도출된 계약 리뷰 데이터이며, 런타임 오류 extension이 아닙니다.

패키지를 추가할 때는 예상 실패를 일반 `Error` 뒤에 숨기지 않음을 증명하는 타입
실패 경로를 최소 하나 테스트하세요.
