# @croco/gamification-core

Cooperative challenges with explicit policy consent, trusted activity receipts, atomic progress and durable completion intents. The service requires a server authorization callback, a current tenant-membership source and explicitly registered activity verifiers. Client-provided progress is never accepted.

A challenge is scoped by application, environment, tenant and challenge ID. Create its versioned definition before the start, then join with the exact policy version and leave policy. Definitions cannot change once any participant has consented or the start has arrived. `memberCap` limits each member's credited progress; `minMembers` counts currently joined members at settlement. Participants may join before the end; only activity occurring within both the challenge interval and one of their consented membership intervals counts.

`contribute` takes a source ID and opaque event ID. The registered verifier resolves a trusted subject, occurrence timestamp, nonnegative safe-integer amount, positive integer revision and optional original event ID (`correctionOf`). Sources must authenticate provenance and return the same occurrence and subject for corrections. Corrections replace an original amount, require a strictly advancing revision and may arrive during the late allowance. Stored acceptance timestamps come from the service clock. Event IDs are hashed before storage and deduplicated across all sources and requests within the scoped challenge. Corrections must come from the source that owns the original accepted event.

Before calling a registered source, the service durably records an unresolved evidence attempt. Attempt identity includes source, requesting subject and event, while accepted event identity is global within the scoped challenge. A rejected claim cannot reserve another subject's or source's delivery. Source verification runs after registration commits and outside the store transaction, so it does not retain a database connection or prevent voluntary leave. Acceptance rechecks authorization and the current membership intervals in a fresh atomic transaction. A source outage preserves that attempt and throws an operational Problem; `pendingEvidenceCount` makes the incomplete aggregate explicit. Settlement refuses unresolved attempts. The caller can explicitly retry the same event and idempotency key, including after the cutoff if the original attempt arrived before it. No automatic retry runs. Valid evidence and its accepted attempt commit together, atomically rejecting other unresolved deliveries of that same globally consumed event because they cannot contribute again; proven invalid evidence is recorded as rejected. Privacy erasure removes the subject's unresolved attempts as well as their activity.

States progress through `scheduled`, `active` and `closing`. Reaching the goal displays progress immediately; final success is decided only by `close` at or after `end + lateAllowanceMs`. This allows legitimate late receipts and corrections to affect settlement. Settlement writes exactly one completion intent when the goal and minimum membership are met, otherwise `expired`. Completion delivery/reward execution belongs to a consumer of the durable intent and requires its own idempotent delivery contract. This package does not claim that storing an intent executes a reward.

The `retain` leave policy retains prior earned progress; `remove` excludes all ended membership intervals permanently, including after rejoining. Leaving withdraws public contribution consent. `read` returns the current subject's membership and progress plus aggregate progress. Only an actively joined reader can view the optional participant projection, and only currently joined members who explicitly consented appear in it; pages default to 20 and are limited to 100. Raw activity and audit records are never part of this projection.

`eraseSubject` deletes membership intervals and raw activity and scrubs matching audit identities. Retain-policy earned progress becomes an anonymous aggregate; remove-policy progress is removed. Already-finalized outcomes remain immutable. Minimal pseudonymous subject suppression and hashed event/request tombstones remain for the lifetime of the scoped challenge to prevent replay and repeated erasure from resetting the per-member cap. An erased subject cannot join or contribute again to that challenge. These tombstones are privacy-relevant retained data and must be included in the application's retention policy; this is not a claim that all stored data is anonymous. Retries never return saved personal snapshots. Every read and retry checks current authorization and current tenant membership. Privacy erasure also requires server authorization, but deliberately permits a former tenant member as the target: the authorization callback must verify the actor's privilege to erase that subject in the requested scope. It does not require the target to retain tenant membership. Audit receipts retain the operation and definition version, including after their identifying fields are scrubbed.

`ChallengeStore.transact` must serialize the entire scoped challenge, including concurrent creation, and atomically persist its challenge, membership, activity, receipts, tombstones and completion intent. Any error must roll back all writes. `InMemoryChallengeStore` implements this contract for tests/development; production requires a durable adapter such as `@croco/gamification-drizzle` and an explicitly applied migration. No schema is created at application startup.
